# 代码审查：对标最终目标

> 目标：**以 wb2api 源码为基础，账号管理 + 翻译 + Zotero 打通的单一软件。傻瓜式。**
> 这次是**读代码**，不是看功能。审完当场抓到两个真 bug，都出在我自己写的代码里。

---

## 一、审查结论

**架构对得起目标，但翻译引擎有三处「报成功而实际没做」的断点，其中两处是我这轮引入的。**

读完 `internal/translate` 全部 1,150 行后的判断：

- 对目标的贴合度：**好**。一个进程、一个端口、串行队列、pdf2zh 子进程 —— 每条都站得住。
- 代码质量：**中**。注释密度高、实测依据写清了，但**防御性逻辑有一处做错了方向**（并发写盘）。
- 最严重的问题：**模型的链路断在中间，而每一层都自报成功。**

---

## 二、两个真 bug（已修，已加测试守住）

### 🔴 BUG-1：模型选择从来没生效过

```go
// translate.go:320 修复前
if model == "" {
    model = "auto"          // ← 硬编码，掐死了下游
}
```

`buildArgs` 里读 `DefaultModel` 的分支因此**永远走不到**（死代码）。于是：

```
面板设置      → default_model = cn:hy3      ✅ 对
GET /translate → 返回 cn:hy3                 ✅ 对
Submit        → job.Model = "auto"          ❌ 断在这
buildArgs     → 发 --model auto             ❌
pdf2zh 请求    → model=auto                 ❌
```

**每一层都"正常"，中间的链路断了。** 用户上一轮报的「我设了 hy3 但用的是 auto」就是这个，而我上一轮的"修复"只改了 `buildArgs` —— 那段代码根本没被执行过。

**我当时怎么验证的**：调 API、确认 `default_model` 往返正确。这恰恰是我在上一份复审里批评自己的错误 —— **验证产物，不验证生成产物的东西**。这次从请求日志验：

```
18:46:54  model=cn:hy3  200     ← 修复后
16:49:34  model=auto    200     ← 修复前
```

### 🟠 BUG-2：并发写盘静默丢写

`saveAsync` 每次起一个 goroutine，全部写同一个 `path + ".tmp"`。

```
64 并发保存实测：43 次 rename 失败（"being used by another process"）
每一次失败 = 这一份快照根本没写进去
```

**我最初把它描述成"数据损坏"，这是错的。** `os.WriteFile` 对整块 buffer 是单次 write syscall，内容不会被撕裂。真实伤害是 **写入静默丢失**：`jobs.json` 落后于内存，重启后最近的状态没了，且没有任何报错给用户。

**突变测试当场抓到我这个说法的问题**：去掉互斥后，我那句「文件仍能解析」的断言**照样通过**。改成断言「并发保存期间零条写盘失败日志」之后才真能抓到。

## 三、按目标逐条评估

### ✅ 账号管理

`internal/pool` 80.3% 覆盖，`internal/session` 79.5%，`internal/usage` 85.6%。
这块是上游代码 + 我几乎没动，**代码质量最好的一部分**。

双号轮换在请求日志里可直接观察，`7487fc9f` / `79be0872` 交替出现。

### ✅ 翻译：链路对，但引擎层曾经 0% 覆盖

架构判断都对：

| 决策 | 位置 | 为什么对 |
|---|---|---|
| 串行队列 | `Queue.loop` | 两个 BabelDOC 各约 1.8 GB |

| 产出落在源同目录 | `Submit` | 插件 syncOnce 在条目目录里找 |
| 三种静默失败分别建模 | `finish` | `produced_nothing` / `partial` / `error` |

**但覆盖率是硬伤**，已从 19.2% 补到 **51.0%**：

|---|---|---|

| `findDualPDFs` | 0% | **92.9%** |

### ⚠️ Zotero 打通：链路通，但版本耦合是隐患

三处清单（仓库源码 / 面板下发 / GitHub 发布）当前完全一致，但**它们是三份独立的副本**：

```
plugin/manifest.json          ← 源
dualsync@zotero.local.xpi     ← 打包产物（面板下发）
GitHub Release 里的 xpi       ← CI 产物
```

一旦有人只改一处，三处会漂移，而**漂移的表现是静默的**（更新永远查不到，或装的不是预期的版本）。
`scripts/build-plugin.py` 有版本自检（包内 manifest 版本必须等于源），但**没有跨副本一致性检查**。

**建议**：加一条 CI 断言 —— 发布后回读 Release 里的 xpi，比对 manifest 的 `version` 与 `update_url`。

### ⚠️ 「单一软件」：仍是 zip 而非安装器

`dist/litflow-1.13.0-windows-x64.zip` 3.8 MB，解压双击即可用，**新装自建配置**（实测）。
但严格说这是「绿色包」，不是「安装器」：没有开始菜单项、没有卸载入口、没有开机自启选项。

对这一版可以接受；要变成"真软件"需要 Inno Setup 之类。

## 四、还剩下什么没测（诚实的清单）

补完测试后，`internal/translate` 仍有 **19 个函数 0%**，按价值排序：

| 函数 | 为什么重要 | 好测吗 |
|---|---|---|
| **`spawn`** | WaitDelay、NO_PROXY、超时杀进程 —— **三条实测教训都在这里** | 需假 pdf2zh |
| **`runOne` / `finish`** | **三种静默失败的分类判据** | 需假 pdf2zh |
| `resolveExe` | 找不到 pdf2zh 时的报错质量 | 易 |
| `CJKCount` / `MarshalJob` / `ElapsedS` / `Liveness` / `lastLine` | 纯函数 | 很容易 |
| `Start` / `Stop` / `loop` / `Counts` | worker 生命周期 | 中 |
| `hideWindow` | Windows 专属 | 难，不值得 |

**`spawn` + `runOne` + `finish` 是真正值得补的那一组** —— 它们是「静默失败」这个项目立意的落地处。
技术方案明确：用 Go 的 `TestMain` 把测试二进制本身当作假 pdf2zh（靠 `GO_TRANSLATE_HELPER` 环境变量切换行为），
就能在不启动真 pdf2zh 的情况下测：退出码非 0、退出码 0 但无产出、有产出但 0 token、正常完成 —— **四种结局全覆盖**。

## 五、代码质量的具体观察

**做得好的**

1. **注释解释 WHY 且带实测数字**。`buildArgs` 里每个参数后面都跟着"删掉会发生什么"，这是这个仓库最值钱的东西。
2. **三种静默失败独立建模**。`ProducedNothing` / `Partial` / `Error` 不挤在一个字段里，界面才不会把它们渲染成"成功"。
3. **`Get`/`List` 返回副本**，避免调用方与 worker 争用 —— 不是所有 Go 代码都注意这点。
4. **原子写 + 损坏文件隔离**，不是简单覆盖。

**需要改的**

1. **防御性代码做错方向**（BUG-2）。加了互斥却以为防的是"损坏"，实际防的是"丢写"。**对失败模式的误判比不写防御更危险** —— 它让人以为问题已经解决了。
2. **硬编码兜底值掐死了上游配置**（BUG-1）。`model = "auto"` 这类"看着安全的默认值"，恰恰让下游的配置读取变成死代码。
3. **`Submit` 里有 6 个提前 return，其中 4 个返回错误、2 个返回 job**。调用方必须读注释才知道"成功"可能是 skipped 而不是 queued。建议返回一个显式的枚举（`submitted` / `deduped` / `skipped`）。

## 六、我的判断

**这两个 bug 有一个共同点：它们都是"两层都正常、中间断了"。**
- 模型：面板正常、接口正常、**Submit 硬编码掐断**
- 写盘：写函数正常、读函数正常、**并发时丢一半**

这类 bug 用「测每一层」的测法永远发现不了 —— 只能**测链路**（请求日志里那个 `model=cn:hy3`）
或者**测并发**（43 次失败）。这解释了为什么我之前那些"验证通过"是假的。

**下一步该做的，按性价比排：**

1. **补 `spawn`/`runOne`/`finish` 的测试**（用 TestMain 假 helper）—— 覆盖四种结局，把「静默失败」真正钉住
2. **加跨副本一致性检查**（CI 回读 Release 的 xpi 比对 manifest）
3. `Submit` 返回显式枚举，让调用方无法把 skipped 当成 queued
4. 补那批纯函数（`CJKCount` 等，半小时）

**不该现在做的**：把 zip 做成安装器（功能还在动）、重写历史去体积（会破坏已发布的 tag）。
