# 按最终目标的严肃评估

> 目标（你定的）：**以 wb2api 源码为基础，一款账号管理 + 翻译 + Zotero 打通的单一软件。傻瓜式。**
> 评估时间 2026-10-17。所有数字取自当前磁盘状态，不是估算。

---

## 一、一句话结论

**功能上，目标达成了 —— 而且有硬证据。工程上，它还没有达到"傻瓜式"该有的可靠性，而缺的正好是全项目唯一没有自动化测试的那一层。**

---

## 二、目标拆解 vs 实测达成度

| 目标 | 状态 | 证据（不是自述） |
|---|---|---|
| **账号管理** | ✅ 达成 | 2 个账号，`7487fc9f` / `79be0872` 双号轮换在请求日志里可直接看到；余额/签到/启停/暂停全在 |
| **翻译** | ✅ 达成 | 实译 270s / 86,833 token、190s / 57,693 token；译文质量你确认"还可以" |
| **Zotero 打通** | ✅ 达成 | **Zotero 库里 37 个 dual 附件已挂、270 次「双语已译」标签落下** |
| **单一软件** | ⚠️ 部分 | 一个二进制 14 MB 同时服务 `/v1` `/panel` `/translate` `/health`；但**它不是一个安装包**（见第四节） |

### 这一节要强调什么

**37 个附件 + 270 个标签** 是这次工作里最硬的一条证据。它说明「Zotero 里选中文献 → 工具菜单 → 翻译 → 双语件回挂并打标签」这条**端到端链路是真的通的**，不是接口层面通了而已。

这条链路里踩过的坑全部记进了提交历史：zip 缺目录条目、`update_url` 既要存在又必须 https、`strict_min_version` 6.999 在 Zotero 10 上不给装、产出写到插件找不到的目录。这些都是"看起来该对但就是不对"的东西。

## 四、结构性缺陷（按严重度排序）

### 🔴 1. 前端 4,497 行，零自动化测试 —— 而它是唯一反复坏的地方

冷数据：这一轮 13 次提交里 **3 次是新功能，10 次是修复**；而 10 次修复中**至少 5 次是在修我自己在本会话里弄坏的东西**：

| 我弄坏的 | 症状 | 为什么没被挡住 |
|---|---|---|
| `apiRoot` 只加了调用没加定义 | 翻译页永远报 `apiRoot is not defined` | 无 JS 测试 |
| 面板资源无 `Cache-Control` | 修好的 bug 原样复现，双方都以为没修对 | 无缓存/冒烟测试 |
| `refreshZotero()` 被某次替换吃掉 | 卡片永远停在「检测中」 | 无 DOM 测试 |
| 把 `update_url` 删掉 | 插件装不上（manifest 校验直接拒） | 无契约测试 |
| 模型开关只写了一半 | 用户"找不到开关" | 无 DOM 测试 |

**Go 后端有 18,661 行测试，所以后端几乎不出事。前端一行测试都没有，所以每次都要靠你在浏览器里发现。** 这不是巧合，是因果。

### 🔴 2. 队列只活在内存里，重启即丢

`jobs map[string]*Job` 没有任何落盘。实测后果：我重启网关，一个正在跑的任务消失，插件对着不存在的 id 轮询（我已改成 404 即终态，但**任务本身还是没了**）。

对一个"翻译 300 页书可以跑一小时"的工具，这是硬伤。

### 🟠 3. 没有任何进程监管

网关这一轮**静默死过两次**，两次都是你看到 `Failed to fetch` 才知道。现在有 `start-litflow.cmd` 可以可靠拉起，但**它死了不会自己回来**。

更隐蔽的是我顺手挖出的第二个：相对路径 `./auths` 依赖工作目录 —— 换个目录启动就是 **`loaded 0 account(s)`，网关照常 200，账号列表空，零报错**。已修（锚定到 config.json 所在目录），但这类"照常工作但什么都没做"的失败形态值得单独警惕。

### 🟠 4. 「一个软件」其实是「一个启动器 + 一个界面 + 853 MB 的 Python 环境」

```
wb2api.exe                14 MB   一个二进制，面板内嵌
pdf2zh_next venv         853 MB   AGPL v3，只能子进程调用
Zotero                  外部应用，装插件
```

**"单一软件"做到的是「一个进程、一个端口、一个界面」，不是「一个安装包、一次安装」。** 这个区别必须说清楚，否则目标是被含糊掉的。AGPL 那条边界（子进程而非链接）是对的，不该为了"更像一个软件"去破它。

### 🟡 5. 插件的自动更新源是假的

`update_url` 现在指 `https://example.com/...`（占位、404）。它能装、能跑，但**永远收不到更新**。要真做，得把你的 `update.json` 放到一个真实 HTTPS 地址（你有 `leobba/Daxiang-zotero-tools` 的权限）。

### 🟡 6. `E:\code\LitFlow` 已经是知识库，不再是产品

运行时（CLI/网关/桌面壳）全部退役，剩下 338 条断言 + `docs/` 的实测记录。它现在的价值是**知识**，不是**代码**。留着对，但要有这个认知。

## 五、架构判断：哪些决策是对的

| 决策 | 判断 | 依据 |
|---|---|---|
| **以 wb2api 为基座**，而不是把它的 23k 行搬出去 | ✅ 对 | 移植 1,740 行进来 vs 搬 23k 行出去，差 13 倍 |
| **一个二进制、一个端口** | ✅ 对 | `/v1` `/panel` `/translate` `/health` 三类调用方共用，14 MB 单文件 |
| **面板和插件共用一套队列 API** | ✅ 对 | 两套面 = 每处改动想两遍，这个项目已经因为这个吃过亏 |
| **pdf2zh 永远子进程** | ✅ 对 | AGPL 边界；且它 853 MB，本来也打不进二进制 |
| **回环免 key、非回环要 key** | ✅ 对 | 插件不带 key（要求用户去 Zotero 偏好里填 key 就破坏傻瓜式），但一刀切免鉴权会把队列暴露给整个局域网 |
| **不合并两个仓库** | ✅ 对 | 许可证边界、两套构建链、两种升级节奏 |
| **队列串行** | ✅ 对 | 两个 BabelDOC 各 ~1.8 GB，并发是 swap 风暴 |
| **不造假进度条** | ✅ 对 | pdf2zh 管线下不吐阶段信息，会动的条只能是编的 |

**架构没有需要推翻的地方。** 问题不在设计，在**没做的那几件事**：持久化、监管、前端测试。

## 六、如果继续做，优先级（我的排序）

| 优先 | 事项 | 为什么排这个位置 |
|---|---|---|
| **1** | **前端冒烟测试**（哪怕只有 20 条：面板能加载、每个 tab 的关键元素在、`apiRoot`/`refreshZotero` 存在、开关能渲染） | 这是唯一反复坏的一层，而它 4,497 行。20 条断言能挡掉这一轮 5 个 bug 里的 4 个 |
| **2** | **队列落盘**（`data/jobs.json`，启动恢复，已完成的保留 N 条） | 一小时的任务不该因为重启消失；且历史记录本来就有用 |
| **3** | **进程监管**（启动器加自愈，或做成计划任务/服务） | "该死就死"对一个要挂后台的工具是根本问题 |
| **4** | **插件更新源指向真实 HTTPS** | 一次性配置；不然插件永远是 1.1.1 |
| **5** | 打包成安装器（exe + 插件 + pdf2zh 引导下载） | 真正的"傻瓜式"在这里，但**前提是 1-3 稳住** |

**先 1，再 2、3。** 因为 1 的成本最低、挡住未来 bug 的收益最高；而 2、3 是让"已经能用的东西"变得可信。

## 七、我不建议做的

1. **Tauri / Electron 重写前端**。面板已经是 `go:embed` 单二进制，重写要引入 Node + Rust 两套链，换来的只是窗口外观。你上次问过，我的答复没变：**推迟，且很可能不需要**。
2. **把 pdf2zh 打进安装包**。853 MB + AGPL 的源码提供义务。正确做法是引导下载或复用已有安装。
3. **合并 `E:\code\LitFlow` 和 wb2api**。两者的关系已经是「知识库 → 产品」，合并只会让两边都变模糊。
4. **为了"更像一个软件"去动 AGPL 边界**（比如把 pdf2zh 改成 import）。这会让整个产品被 AGPL 传染。

---

## 八、一个不舒服但要说的判断

这一轮里，功能是我加的，但**大部分的返工也是我造成的**：前端 5 个 bug 是 5 次"看起来改完了"，插件安装的 4 轮里有 2 轮是我的错判（先怪目录条目、再删 `update_url`）。

值得记下来的不是"AI 会犯错"，而是**错误的分布是有规律的**：
- 有测试的地方（Go，18,661 行测试）→ 几乎不出事
- 没测试的地方（前端 4,497 行、插件集成、安装链路）→ 反复出事

所以最有价值的下一步不是加功能，是**把那 4,497 行纳入测试**。这是这次评估里唯一一条我认为是"必须"而不是"建议"的。
